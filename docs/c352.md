# Namco C352 sample support (0.9.31)

VGM 1.71 command `0xE1` (16-bit address, 16-bit data) and ROM block `0x92`
are converted to 32 Furnace channels per chip instance. The register model
is libvgm `c352.c`. C219 stays unsupported and is not folded into this path.

Furnace 0.6.8.3 reserves system id `0xD0` for Namco C352 and marks it
unavailable. There is no `DIV_SYSTEM_C352` and no C352 instrument type.
The module still writes chip `0xD0` and Amiga instruments (type 4), which
C140 channels already accept, so a future core copied from `c140.cpp` can
play the samples. The bundled player does not render these channels. The
gap is recorded in the module comment, not as a per-file warning.

## Clock

Header `0xDC` is the input crystal. A typical value is 24192000. Bit 31
mutes the rear pair. Header `0xD6` is the hardware divider divided by 4. A
typical byte is 72, meaning a divider of 288.

The output sample rate is `header_clock / (byte * 4)`. libvgm's core always
divides by 288, so it is given `header_clock * 72 / byte`. With byte 72 that
is the header crystal. A missing divider byte (0) with a crystal-sized clock
keeps the crystal. A sub-megahertz header with divider 1 is the legacy
pre-scaled form: 336000 becomes 24192000. An extra-header clock (device id
`0x27`) is used as a crystal when the main field does not resolve, and the
divider byte is not applied to it a second time.

A voice plays `clock * freq / (288 * 65536)` ROM bytes per second.
`24192000 * 0x8000 / (288 * 65536)` is 42000 Hz. The `.fur` flag
`customClock` carries that crystal. Furnace has no C352 default, so the
flag is always written.

A core copied from `c140.cpp` ticks at clock/192, which is 1.5× this rate.
That port needs the same 2/3 clock scale the C140 flag already uses. This
converter stores the real crystal.

The player default volume for C352 is `0x40` (0.25 against the YM2151).
There is no Furnace core to calibrate, so the module writes 0.25. Two
instances divide that first, the same way the other chips do.

## Voices

Each voice is eight uint16 registers at `voice * 8 + reg`:

| reg | field |
| --- | --- |
| 0 | front volume, high = left, low = right |
| 1 | rear volume, same packing |
| 2 | frequency |
| 3 | flags |
| 4 | wave bank |
| 5 | wave start |
| 6 | wave end |
| 7 | wave loop |

`0x202` strobes key on/off for every voice. The written value is ignored.
The hit time is the strobe, not the flag write. Key-on wins when both bits
are set. The shadow copy clears the bit that fired, so a later strobe does
not restart the voice. A retrigger sets the previous hit's end and does not
emit a separate note-off. An explicit key-off does.

A flags write that clears bit 15 (BUSY) silences the voice at the write,
key-off bit or not: libvgm keeps playing only BUSY voices, and drivers end
notes exactly that way (0x0000 or 0x2000 over the flags). A KEYOFF strobe
after such a write adds nothing. A clear that is followed by a key-on at
the next strobe stays one note, so the driver's clear-then-key pattern does
not cut the replacement.

The default mix is `L = min(255, front L + rear L)` and the same for the
right. Bit 31 of the clock keeps the front pair only. The pattern column is
`max(L, R)`. A hit keyed at zero that later rises is a fade-in: the key-on
row omits `08xy`, because that effect would mute the voice for good. The
first volume write inside that same frame is the note's own balance: Ridge
Racer 2 writes it ~8 ms after the strobe (8694 of 9711 hits) and zeroes the
register when it stops a voice, so without the refit each attack played at
whatever the previous note left behind - usually silence.

Frequency writes inside one 60 Hz frame (735 VGM samples) of key-on, or the
first write when key-on frequency is 0, are the note pitch. These System
11/12 drivers strobe first and write the note's own pitch right after, in
the same frame - the register at the strobe is the previous note's value
(Tekken 2 "19 Ending BGM": 232 hits, up to +18.9 st; Ridge Racer 2: 1032).
Later writes become the same 1/64-semitone slides the C140 path uses.

## Samples

The full address is `(bank << 16) | low16`, and every read folds through the
ROM window: libvgm's core reads `wave[pos & pow2_mask(size)]`, so bits above
the declared block size alias the low ones. Drivers hand the chip
0x80B1D1AE-style addresses (a ROM base byte on the 24-bit offset) and the
converter must fold them the same way or drop the note (Tekken 2 17 Mid Boss
lost 1037 of 2587 triggers that way). Forward playback is contiguous in that
32-bit space, including a wrap across the 64K bank boundary and across the
top of the window.

- One-shot: the fetch at `wave_end` is silenced, so the body is
  `[start, end)` and the length is `(end - start) mod 65536`. A span of 0
  is empty and is dropped.
- Forward loop: the end byte is heard, then playback jumps to `wave_loop`
  in the arrival bank. Length is the one-shot span plus one. The loop point
  is kept when it falls inside that body. When it falls *outside* it -
  Tekken Tag 05 writes `wave_end 0x...8d` with `wave_loop 0x...8e`, one byte
  past the end - the chip jumps to the contiguous byte and plays a full bank
  there (until the low 16 bits meet `wave_end` again), so the body carries
  that region as a second segment and the loop sits at the join. Without it
  the sample plays its intro once and stops. The region is only carried when
  a hit of that body reaches it: a note the driver stops before the running
  address reaches `wave_end` never loops, so its payload stays the intro.
- Mid-note geometry rewrites (start/end/loop/bank writes with no strobe): the
  chip jumps with the live registers when the running address reaches
  `wave_end`, and these drivers pair each key-on with a rewrite 8 ms later
  (`start=0x4cd4` / `loop=0x009b`, then `start=0x009b` / `loop=0x928e`). The
  rewrite points the LINK jump at the byte after the intro - the sample's
  real continuation - while the key-on pair would send it to a far-away
  address that folds into unrelated ROM. The converter records the
  `wave_start`/`wave_loop` a rewrite leaves while the voice has not crossed
  yet and plans the jump and the region from them; the intro, `wave_end` and
  the bank keep their key-on values (these drivers also rewrite those, but
  as stop/shorten tricks), and a write that lands after the crossing belongs
  to the next pass. Before this, any note that rang past the intro played
  that unrelated ROM as a seamless loop - the distorted tail on Tekken Tag
  05 channel 14 (`C352 1-14`, voice 13).
- Reverse one-shot: playback walks down from start until `wave_end`, which
  is silenced. When start is above end, the body is `[end + 1, start]`
  reversed so Furnace plays it forward. When start is below end the walk
  crosses the bank boundary first, so the body is that descending run
  (`[prev_bank:end + 1, base]`); at bank 0 the walk would leave the ROM
  window, where the reference reads nothing, so the voice is silent and
  counted in the warning. start == end is empty.
- Ping-pong (`LOOP` and `REVERSE`): the body is `min(loop, end)` through
  `max` inclusive, looped in Furnace mode 2. When `wave_start` is below the
  region, the pre-attack is kept: the body starts at the written start and
  the loop sits at the region, which is where the first pass turns around.
- `LINK` without `LOOP` is a one-shot of the first segment. `LINK` with
  `LOOP` jumps to `(wave_start << 16) | wave_loop`, using wave start as the
  high 16 bits. When that target is the ordinary in-bank loop, the ordinary
  loop is used. Otherwise the intro (inclusive of the end byte) is
  concatenated with the loop region and the loop starts at the join. A
  target outside the dump plays the intro once and does not loop (fixture
  renders show the reference reads nothing past the window), so a voice the
  source lets go quiet cannot drone on in the module. Bodies are capped at
  1 Mi frames. A driver that rewrites a LINK voice's geometry mid-note (no
  strobe) does not get a new body: the note keeps what its key-on
  extracted.

Linear samples stay signed 8-bit. Mulaw uses the C352 table from
`device_start_c352` (byte `0x01` is int16 32) and is stored as linear int16
so Furnace does not decode it with another law. Bytes are reversed before
the mulaw expand. Trailing silence is trimmed without cutting a loop.
A trigger whose base address (after the window fold) is not inside a dumped
slice is counted and dropped, so a hole filled with zeros is not treated as
a real sample.

## Left out

Phase invert, the FM flag, the interpolation-disable bit, noise, and the
hardware volume slew are not applied. The slew at musical frequencies is a
few milliseconds; the pattern receives the target registers. Noise voices
produce a warning and no note. Mid-note changes to the end address are not
re-extracted. Ping-pong stores the bounce region and lets Furnace start at
the low address going forward. Pitch sweeps are written as per-row ramps; a
constant-rate glide keeps its effect on every row (0.9.32), but fast
E8xx/E9xx quick-legato sweeps can still settle a few semitones short - see
docs/testing-pipeline.md open items.

## Playback today

The bundled Furnace 0.6.8.3 still refuses a `0xD0` module at load with
`unrecognized system ID d0`. A local core now exists: `furnace/` holds a
Furnace checkout with a C352 system bound to `0xD0`, ported from libvgm
`c352.c` onto the dispatcher pattern of `platform/c140.cpp`. The headless
build lives at `furnace/build/furnace.exe`, which the tools in this project
find automatically (`VGM2151FUR_FURNACE` overrides the search). To listen,
use the GUI build at `furnace/build-gui/Release/furnace.exe` - launch it
with a module path or open the `.fur` from the file dialog; C352 sits in the
Sample category of the add-chip menu. It is not
upstream: furnace pull request 2901 was closed in August 2026 without a
working core, and the fork still in progress (`BSDnux/furnace-ports`, branch
`C352`) uses system id `0xe8` and C219-format sample bytes instead, so it
does not open these files.

The core reads the chip's raw bytes. Linear bodies go in as signed 8-bit
PCM; the mu-law bodies this converter stores as 16-bit values are re-encoded
to C352 mu-law bytes at upload and the MULAW flag is set. Voices tick at
`clock/288` and `customClock` carries the real crystal, so a sample's stored
`c4_rate` plays at the recorded rate. LINK bodies whose loop crosses a bank
are placed as two segments and driven through the chip's LINK jump. The
frequency register is written before the key-on strobe, the way drivers
write the hardware, so the register image the strobe sees is
self-contained.

## VGM export and the register audit

The core exports VGM (`vgmVersion` 0x171): command `0xE1` (bit 15 of the
address selects the second instance), ROM block `0x92`, divider byte 72
(`/288`), and the header clock is the crystal. `fur2vgm.py` and
`fur_soundcheck.py` therefore work on C352 modules like on C140 ones.

Register-level diff of the exports against the sources, run through the
converter's own C352 model so both sides are read the same way:

| track | samples | hits | frequency | volumes | flags |
|---|---|---|---|---|---|
| Tekken Tag 05 | 22/22 | 1712/1712 | median +0.11%, max 0.15% | 98 of 1712 outside the 16-step volume column, max 18/255 | LINK folded to LOOP (366 hits), rest equal |
| SoulCalibur 03 | 41/41 | 4457/4458 | median +0.11% | 2292 of 4457, max 32/255 (column resolution) | equal |

Sample bodies are byte equal (21 of 22 hashes on track 05; the 22nd is the
LINK body the core places as two segments and the converter folds into
one). Hit times move within the `.fur` row grid only. The frequency residue
is C-4 rate rounding; the volume residue is the tracker column (16 steps)
that the core feeds back into the chip registers.

Restarts denser than the row grid are tightened like on SegaPCM: Tekken Tag
track 05's drum roll keys 61 times at ~370-sample spacing, so its grid
shrank from row 735 to row 364 (speed 4, 145 orders) and every restart has
its own row. Tracks whose restarts already fit keep their grid.

Soundcheck over the pack (best shift / median, clocks source -> export):

|---|---|---|---|
| Tekken Tag 05 | 0 / 0.993 | 0 / 0.993 | 25401600 -> 25401600 |
| Tekken Tag 16 | 0 / 0.966 | 0 / 0.966 | 25401600 -> 25401600 |

module's 15.1s; the module contains the same events, so that is a grid
question for the jingle, not the core.

## Levels

`.fur` render (Furnace) against the source render, RMS, ten canaries: 0.73
Tekken Tag 05, 0.69 Ace Driver 06, 0.62 Tekken 3 "Eddy", 0.49 Outfoxies 01,
0.49 Cyber Commando 04, 0.42 Tekken "Windermere, UK", 0.40 Tekken 2 "Lei
Wulong", 0.30 Ridge Racer 01, 0.23 Ridge Racer 2 01, 0.21 SoulCalibur "The
New Legend". The reference renderer reads the exports 4-13x below the
sources with registers, bodies, clocks and device lists all equal, a
mix-metadata property of Furnace exports shared by every chip, not a
register difference. No constant correction is justified for the converter:
`_FURNACE_VOLUME_SCALE` stays at unity for `0x27` (the low family tracks the
sample depth, not the mix). The depth-16 family is an open measurement.

Two converter bugs came out of this round: modules with no FM key-ons used
to carry an empty YM2151 (a dead second device in every export), and with
FM off the sample-chip channels must shift down by the missing 8-channel FM
block - without that, hits on voices 24-31 fell off the end of the module.

## Auditing a conversion

    cd vgm2151fur
    python tools\fur_soundcheck.py "<source.vgm|vgz>" "<path>.fur"

Renders the source, the `.fur` and an exported VGM, prints the pitch-shift
table for both pairs plus the Dev lines, so chip clocks can be compared.
Healthy: best shift 0 in both pairs and equal clocks. The rest of the
battery - `tools\c352_regdiff.py` (register-level diff against the source),
`tools\c352_window_scan.py` (per-window spectral comparison, pass 1 only)
and `tools\c352_voice_solo.py` (per-voice isolation) - and the acceptance
numbers are in `docs/testing-pipeline.md`; `tools\reconvert_c352.py`
reconverts the whole C352 set. `pitch_shift.py` and `renderer.py` are the
pieces.

Byte-level verification still stands: on Tekken Tag Tournament track 05, all
22 sample bodies in the `.fur` match the analyzer's regions in bytes, frame
count, depth, C-4 rate, loop range and name - now cross-checked by playback
and by the exported VGM's ROM block.
