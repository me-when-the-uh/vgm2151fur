# Namco C352 sample support

VGM 1.71 command `0xE1` (16-bit address, 16-bit data) and ROM block `0x92`
convert to 32 Furnace channels per chip instance. The register model is
libvgm `c352.c`. C219 stays unsupported and is not folded into this path.

Furnace reserves system id `0xD0` for the C352 and marks it unavailable,
and there is no C352 instrument type. The module still writes chip `0xD0`
and Amiga instruments (type 4), which C140 channels already accept, so a
core ported from `c140.cpp` can play the samples. A build without a C352
core refuses the module at load; the gap is recorded in the module comment,
not as a per-file warning.

## Clock

Header `0xDC` is the input crystal (typically 24192000). Bit 31 mutes the
rear pair. Header `0xD6` is the hardware divider divided by 4 (typically 72,
meaning a divider of 288).

The output sample rate is `header_clock / (byte * 4)`. libvgm's core always
divides by 288, so it is given `header_clock * 72 / byte`. With byte 72 that
is the header crystal. A missing divider byte (0) with a crystal-sized clock
keeps the crystal. A sub-megahertz header with divider 1 is the legacy
pre-scaled form: 336000 becomes 24192000. An extra-header clock (device id
`0x27`) is used as a crystal when the main field does not resolve, and the
divider byte is not applied to it a second time.

A voice plays `clock * freq / (288 * 65536)` ROM bytes per second, so
`24192000 * 0x8000 / (288 * 65536)` is 42000 Hz. The `.fur` flag
`customClock` carries the crystal. Furnace has no C352 default, so the flag
is always written. A core ported from `c140.cpp` ticks at clock/192, 1.5x
this rate, and needs the same 2/3 clock scale the C140 flag uses; this
converter stores the real crystal.

The player default volume for the C352 is `0x40` (0.25 against the YM2151).
There is no Furnace core to calibrate against, so the module writes 0.25.
Two instances divide that first, the same way the other chips do.

## Voices

Each voice is eight uint16 registers at `voice * 8 + reg`:

| reg | field |
| --- | --- |
| 0 | front volume, high = left, low = right |
| 1 | rear volume, same packing |
| 2 | frequency |
| 3 | flags |
| 4 | wave bank |
| 5 | wave start |
| 6 | wave end |
| 7 | wave loop |

`0x202` strobes key on/off for every voice; the written value is ignored and
the hit time is the strobe, not the flag write. Key-on wins when both bits
are set. The shadow copy clears the bit that fired, so a later strobe does
not restart the voice. A retrigger sets the previous hit's end and does not
emit a separate note-off. An explicit key-off does.

A flags write that clears bit 15 (BUSY) silences the voice at the write,
key-off bit or not: libvgm keeps playing only BUSY voices, and drivers end
notes exactly that way (writing `0x0000` or `0x2000` over the flags). A
KEYOFF strobe after such a write adds nothing. A clear followed by a key-on
at the next strobe stays one note, so the driver's clear-then-key pattern
does not cut the replacement.

The default mix is `L = min(255, front L + rear L)`, and the same for the
right; bit 31 of the clock keeps the front pair only. The pattern column is
`max(L, R)`. A hit keyed at zero that later rises is a fade-in: the key-on
row omits `08xy`, because that effect would mute the voice for good. The
first volume write inside the same frame is the note's own balance; some
drivers write it a few ms after the strobe and zero the register when they
stop a voice, so without that refit each attack would play at whatever the
previous note left behind, usually silence.

Frequency writes inside one 60 Hz frame (735 VGM samples) of key-on, or the
first write when the key-on frequency is 0, are the note pitch. Some drivers
strobe first and write the note's own pitch right after, in the same frame:
the register at the strobe is the previous note's value. Later writes become
the same 1/64-semitone slides the C140 path uses.

## Rear pair

The fold above is what a stereo rendition wants, and it is the default. With
`--c352-quad` the front and rear pairs are kept apart instead: the note's four
registers ride on the four pan slots (`81xx`/`82xx` front, `89xx`/`8Axx`
rear, each an exact 8-bit side) with the volume column held wide open, since
the platform scales a voice's level into all four (`outVol * pan / 255`). The
chip's flags then carry `quadOutput=true`, which is what makes the core feed
four outputs instead of summing the pairs itself.

Only a track whose source writes register 1 at all is converted this way; a
source that leaves the rear silent keeps the folded file byte for byte. A
stereo mixdown of a quad module sums the pairs back to the level the fold
produced, so the difference is the pan resolution and the point where the
fold saturates at 255.

## Samples

The full address is `(bank << 16) | low16`, and every read folds through the
ROM window: libvgm's core reads `wave[pos & pow2_mask(size)]`, so bits above
the declared block size alias the low ones. Drivers hand the chip
0x80B1D1AE-style addresses (a ROM base byte on the 24-bit offset) and the
converter must fold them the same way or drop the note. Forward playback is
contiguous in that 32-bit space, including a wrap across the 64K bank
boundary and across the top of the window.

- One-shot: the fetch at `wave_end` is silenced, so the body is
  `[start, end)` and the length is `(end - start) mod 65536`. A span of 0
  is empty and is dropped.
- Forward loop: the end byte is heard, then playback jumps to `wave_loop`
  in the arrival bank. Length is the one-shot span plus one. The loop point
  is kept when it falls inside that body. When it falls *outside* it (a
  `wave_loop` one byte past `wave_end`), the chip jumps to the contiguous
  byte and plays a full bank there, until the low 16 bits meet `wave_end`
  again, so the body carries that region as a second segment and the loop
  sits at the join. Without it the sample plays its intro once and stops.
  The region is only carried when a hit of that body reaches it: a note the
  driver stops before the running address reaches `wave_end` never loops.
- Mid-note geometry rewrites (start/end/loop/bank writes with no strobe):
  the chip jumps with the live registers when the running address reaches
  `wave_end`, and some drivers pair each key-on with a rewrite a few ms
  later whose start/loop points the LINK jump at the byte after the intro,
  the sample's real continuation. The converter records the
  `wave_start`/`wave_loop` a rewrite leaves while the voice has not crossed
  yet and plans the jump and the region from them; the intro, `wave_end`
  and the bank keep their key-on values (these drivers also rewrite those,
  as stop/shorten tricks), and a write that lands after the crossing
  belongs to the next pass. The key-on pair alone would send the jump to a
  far-away address that folds into unrelated ROM, which then plays as a
  seamless loop for any note that rings past the intro.
- Reverse one-shot: playback walks down from start until `wave_end`, which
  is silenced. When start is above end, the body is `[end + 1, start]`
  reversed so Furnace plays it forward. When start is below end the walk
  crosses the bank boundary first, so the body is that descending run
  (`[prev_bank:end + 1, base]`); at bank 0 the walk would leave the ROM
  window, where the reference reads nothing, so the voice is silent and
  counted in the warning. start == end is empty.
- Ping-pong (`LOOP` and `REVERSE`): the body is `min(loop, end)` through
  `max` inclusive, looped in Furnace mode 2. When `wave_start` is below the
  region, the pre-attack is kept: the body starts at the written start and
  the loop sits at the region, where the first pass turns around.
- `LINK` without `LOOP` is a one-shot of the first segment. `LINK` with
  `LOOP` jumps to `(wave_start << 16) | wave_loop`, using wave start as the
  high 16 bits. When that target is the ordinary in-bank loop, the ordinary
  loop is used. Otherwise the intro (inclusive of the end byte) is
  concatenated with the loop region and the loop starts at the join. A
  target outside the dump plays the intro once and does not loop, so a
  voice the source lets go quiet cannot drone on in the module. Bodies are
  capped at 1 Mi frames. A driver that rewrites a LINK voice's geometry
  mid-note (no strobe) does not get a new body: the note keeps what its
  key-on extracted.

Linear samples stay signed 8-bit. Mulaw uses the C352 table from
`device_start_c352` (byte `0x01` is int16 32) and is stored as linear int16
so Furnace does not decode it with another law. Bytes are reversed before
the mulaw expand. Trailing silence is trimmed without cutting a loop. A
trigger whose base address (after the window fold) is not inside a dumped
slice is counted and dropped, so a hole filled with zeros is not treated as
a real sample.

## Left out

Phase invert, the FM flag, the interpolation-disable bit, noise, and the
hardware volume slew are not applied. The slew at musical frequencies is a
few milliseconds; the pattern receives the target registers. Noise voices
produce a warning and no note. Mid-note changes to the end address are not
re-extracted. Ping-pong stores the bounce region and lets Furnace start at
the low address going forward.

Pitch sweeps are written as per-row ramps; a constant-rate glide keeps its
effect on every row. A move too steep for a row's slide goes through
E8xx/E9xx quick legato, and on the sample chips that is an absolute pitch
set in the note's domain, not the relative transpose the FM platform
performs, so the converter writes the whole-semitone offset the trajectory
wants against the note drift the effect itself causes and restarts the
slides from the legato value.

## VGM export

A C352-capable core exports VGM (`vgmVersion` 0x171): command `0xE1` (bit 15
of the address selects the second instance), ROM block `0x92`, divider byte
72 (`/288`), and the header clock is the crystal. `fur2vgm.py` and
`fur_soundcheck.py` then work on C352 modules like on C140 ones.

## Auditing a conversion

    cd vgm2151fur
    python tools\fur_soundcheck.py "<source.vgm|vgz>" "<path>.fur"

Renders the source, the `.fur` and an exported VGM, prints the pitch-shift
table for both pairs plus the Dev lines, so chip clocks can be compared.
Healthy: best shift 0 in both pairs and equal clocks. The rest of the
battery: `tools\c352_regdiff.py` (register-level diff against the source),
`tools\c352_window_scan.py` (per-window spectral comparison, pass 1 only)
and `tools\c352_voice_solo.py` (per-voice isolation). `pitch_shift.py` and
`renderer.py` are the pieces.
